## 들어가며 — 왜 이 프로젝트를 시작했는가

경기도를 방문하는 외국인 여행객이 연간 수백만 명에 달하는 지금, 우리는 역설적인 문제를 목격하고 있었습니다. 정보는 넘쳐나지만, **'지금 내 위치 근처에서, 현재 날씨에 어울리는, 진짜 현지인이 추천하는 곳'** 을 찾는 것은 여전히 어렵고 단편적인 경험으로 남아 있었습니다.

구글 지도를 열면 별점이 나오지만, 그 별점이 왜 높은지, 봄비가 내리는 날 실내 관람이 가능한지, 아이와 함께 가도 좋은지 같은 문맥적(Contextual) 정보는 사용자가 여러 탭을 열어 직접 취합해야 합니다. 이것이 우리가 LALA 프로젝트를 시작한 근본적인 이유였습니다.

**"검색이 아니라 대화를. 링크가 아니라 맥락을. 키워드가 아니라 이야기를."**

LALA는 단순히 '근처 맛집을 추천해 주는 앱'이 아닙니다. 수천 개의 블로그 리뷰를 학습하고, 현재 날씨 데이터를 실시간으로 반영하며, 마치 현지 친구처럼 방문객의 귀에 대고 속삭이듯 장소의 이야기를 들려주는 **위치 기반 AI 도슨트 서비스**입니다. 이 시리즈는 그 시스템을 어떻게 설계하고 구현했는지에 대한 완전한 기술적 여정을 기록합니다.

## 1. 기존 서비스들의 한계 — 우리가 해결하려 했던 문제

### 1.1 키워드 검색의 한계: 맥락을 잃은 정보

기존의 추천 시스템은 대부분 키워드 기반 텍스트 매칭에 의존합니다. 사용자가 "카페"를 검색하면 "카페"라는 단어가 포함된 장소가 노출됩니다. 이것은 간단한 케이스에서는 잘 동작하지만, 다음과 같은 시나리오에서는 철저히 실패합니다:

- 사용자가 "비 오는 날 혼자 책 읽기 좋은 조용한 카페"를 원할 때, 키워드 검색은 단순히 근처의 모든 카페를 나열합니다.
- "여름 폭염에 아이들과 방문하기 좋은 실내 명소"라는 질문에, 기존 시스템은 '실내'와 '아이'를 각각 필터링할 수는 있어도 그 두 조건이 만족하는 **경험을 설명해 줄 수 없습니다**.
- 외국인 여행객이 "여기서 뭘 하면 좋을까요?"라고 물었을 때, 단순 별점 목록은 맥락 없는 숫자에 불과합니다.

키워드 검색의 근본적인 한계는 **의미(Semantic)**가 아닌 **형태(Syntactic)**를 기준으로 작동한다는 점입니다. "야외 산책"과 "공원 피크닉"은 의미적으로 가깝지만, 키워드 매칭 시스템에는 전혀 다른 두 문자열입니다.

### 1.2 실시간 컨텍스트의 부재

더 큰 문제는 추천이 **정적(Static)**이라는 것입니다. 오늘 미세먼지 농도가 150µg/m³인 날과 맑고 청명한 날, 같은 야외 명소를 동등하게 추천하는 것은 사용자 경험을 오히려 해칩니다. 기존 서비스들은 이 실시간 환경 데이터와 추천 로직 사이에 아무런 연결고리가 없었습니다.

### 1.3 일방향 정보 전달의 한계

기존의 관광 안내는 명판, 브로슈어, 앱 텍스트처럼 일방향입니다. 방문객은 정보를 소비할 뿐, 그 장소의 '이야기'를 느끼기가 어렵습니다. 반면 수원 화성의 축성 과정, 광교 호수공원에 얽힌 지역 커뮤니티의 이야기, 주말 오후에 가장 맛있는 메뉴가 무엇인지 같은 **살아있는 이야기**는 Naver 블로그와 당근마켓 커뮤니티 포스트에 흩어져 있습니다.

이 흩어진 이야기들을 AI가 취합하고, 사용자의 현재 위치와 날씨에 맞춰 가공하여, 이어폰으로 들을 수 있는 음성 도슨트로 전달하는 것. 이것이 LALA가 목표하는 바였습니다.

## 3. 핵심 결정: 왜 Cosmos DB 대신 PostgreSQL을 선택했는가

Azure 클라우드 환경에서 데이터베이스를 선택할 때, 가장 먼저 고려 대상에 오른 것은 당연히 **Azure Cosmos DB**였습니다. Microsoft의 퍼스트파티 NoSQL 서비스이고, 글로벌 분산, 99.999% SLA, 수평적 스케일링 등 화려한 스펙을 갖추고 있습니다. 그러나 우리는 최종적으로 **Azure Database for PostgreSQL Flexible Server**를 선택했습니다. 이 결정의 근거를 세 가지 축으로 정리합니다.

### 3.1 비용 모델의 근본적인 차이 — RU/s 과금의 리스크

Cosmos DB는 **Request Unit(RU)**이라는 독자적인 용량 단위를 사용합니다. 1 RU는 대략 1KB 항목에 대한 1회 포인트 읽기를 의미하며, 모든 읽기/쓰기/인덱싱 작업은 이 RU를 소비합니다. 문제는 **RU/s를 사전에 프로비저닝하거나, 서버리스(Serverless) 모드를 사용해야** 한다는 점입니다.

LALA 프로젝트는 다음과 같은 워크로드 특성을 가집니다:

- **배치성 고부하 구간**: `review_pipeline_func`가 매일 새벽 2시에 수백~수천 개의 블로그 리뷰를 처리하고 임베딩 벡터를 일괄 삽입합니다. 이 순간 RU 소비가 폭발적으로 증가합니다.
- **평상시 저부하 구간**: 배치가 끝난 낮 시간에는 iOS 앱의 장소 조회 요청만 들어오며, RU 소비가 극히 낮습니다.
- **예측 불가능한 트래픽**: 특정 행사나 언론 보도 이후 앱 사용자가 급증하는 경우, RU/s를 얼마나 프로비저닝해야 할지 예측하기 어렵습니다.

Cosmos DB의 프로비저닝된 처리량 모드에서는 최소 400 RU/s부터 과금이 발생하며, 피크 부하를 지탱하기 위해 높게 설정한 RU/s는 평상시에도 고스란히 비용으로 나갑니다. 서버리스 모드는 사용한 만큼만 과금하지만, 100만 RU당 약 $0.25 수준으로 배치 처리가 집중되는 구간에는 예상치 못한 청구가 발생할 수 있습니다.

반면 **PostgreSQL Flexible Server는 vCore 기반 과금**입니다. Burstable B2s 인스턴스(2 vCore)를 선택하면 평상시에는 낮은 CPU 사용률로 저렴하게 운영되고, 배치 처리 구간에는 CPU 버스팅을 활용합니다. 무엇보다 **쿼리를 아무리 복잡하게 작성해도 추가 과금이 없습니다**. 벡터 유사도 검색 100만 번을 돌려도 RU 초과 비용을 걱정할 필요가 없습니다.

```
[비용 비교 시나리오 — 월 100만 건 문서 읽기 + 10만 건 벡터 검색 기준]

Cosmos DB (서버리스):
  - 문서 읽기: 1,000,000 × 1 RU = 1,000,000 RU = $0.25
  - 벡터 검색 (pgvector 유사 기능 DiskANN): 별도 RU + 기능 제한
  - 스토리지: 1GB당 $0.25/월
  - 최소 월 예상: $50~$200 (피크 부하 프로비저닝 포함)

PostgreSQL Flexible Server (Burstable B2s):
  - 컴퓨팅: ~$30/월 (고정)
  - 스토리지: 32GB 포함, 초과분 $0.115/GB
  - pgvector 쿼리: 추가 비용 없음
  - 최소 월 예상: $35~$50 (예측 가능한 고정 비용)
```

초기 스타트업 또는 POC(Proof of Concept) 단계에서 **비용 예측 가능성**은 매우 중요합니다. RU/s 모델은 설계 단계에서 정확한 워크로드를 예측하기 어려울 때 과도한 프로비저닝이나 예상치 못한 과금으로 이어질 수 있습니다.

### 3.2 데이터의 정형성과 관계의 중요성 — NoSQL이 오히려 약점이 되는 구조

Cosmos DB가 강력한 것은 **스키마 유연성(Schema-less)**과 **Document 모델**이 필요할 때입니다. JSON 문서를 그대로 저장하고, 필드 구조가 문서마다 달라도 되며, 중첩된 계층 구조가 자연스러운 경우가 그렇습니다.

그러나 LALA의 데이터 모델을 살펴보면 이와 다른 특성을 갖고 있습니다:

```
locallink.gyeonggi_attractions  ←─────────────────────────────────┐
  (관광지 정보, 1개 레코드)                                          │
         │                                                          │
         │ 1:N 관계 (하나의 관광지 → 여러 블로그 리뷰)               │
         ▼                                                          │
locallink.attraction_reviews                                       │
  (리뷰 텍스트 + 임베딩 벡터, N개 레코드)                            │
         │                                                          │
         │ 1:1 관계 (리뷰 집계 → 도슨트 정보)                        │
         ▼                                                          │
locallink.attraction_details                                       │
  (LLM 요약, 분위기 키워드)                                          │
         │                                                          │
         │ JOIN (attraction_name 기준)                              │
         ▼                                                          │
locallink.realtime_weather_conditions                              │
  (현재 날씨, 배치 업데이트)                                         │
         │                                                          │
         └──────── 종합하여 ──────────────────────────────────────▶│
                                                           RAG 프롬프트 컨텍스트 구성
```

이 구조는 명확한 **외래키(Foreign Key) 관계**와 **다중 테이블 조인**이 핵심입니다. RAG 추론을 위한 컨텍스트를 구성할 때, 관광지 기본 정보, 관련 리뷰 벡터들, 현재 날씨 상태, 도슨트 캐시를 한 번의 조인 쿼리로 가져올 수 있다는 것은 PostgreSQL의 핵심 강점입니다.

Cosmos DB에서 이를 구현하려면 **비정규화(Denormalization)**가 필요합니다. 즉, 각 문서에 관련된 모든 정보를 중복 저장해야 합니다. 이는 데이터 일관성 유지를 어렵게 하고, 특히 날씨 정보처럼 자주 업데이트되는 데이터를 수백 개의 관광지 문서에 동기화하는 과정에서 심각한 복잡도를 야기합니다.

```sql
-- PostgreSQL의 힘: 하나의 쿼리로 RAG 컨텍스트 전체 구성
SELECT
    a.attraction_name,
    a.road_address,
    ad.summary_ko,
    ad.atmosphere_ko,
    ad.tips_ko,
    w.temperature,
    w.is_rain_snow,
    w.is_bad_dust,
    w.pm10,
    ar.clean_text,          -- 벡터 유사도 상위 리뷰들
    ar.embedding <=> $1 AS cosine_distance  -- pgvector 코사인 거리
FROM locallink.gyeonggi_attractions a
LEFT JOIN locallink.attraction_details ad ON a.attraction_name = ad.attraction_name
LEFT JOIN locallink.realtime_weather_conditions w ON w.location = a.city_county_name
LEFT JOIN locallink.attraction_reviews ar ON ar.attraction_name = a.attraction_name
WHERE a.attraction_name = $2
ORDER BY ar.embedding <=> $1  -- 질문과 가장 관련된 리뷰 우선
LIMIT 8;
```

이 쿼리를 Cosmos DB에서 구현하려면 컨테이너 간 조인이 불가능하므로, 여러 번의 포인트 읽기를 애플리케이션 레이어에서 조합해야 합니다. 이는 코드 복잡도 증가, 레이턴시 증가, 일관성 문제로 이어집니다.

### 3.3 초기 페이즈에서의 오버엔지니어링 방지 — 성숙한 엔지니어링의 조건

엔지니어링에서 가장 어려운 결정 중 하나는 **"얼마나 미래를 대비해야 하는가"** 입니다. Cosmos DB의 글로벌 분산, 멀티 리전 쓰기 같은 기능은 분명 매력적입니다. 그러나 현재 LALA의 서비스 범위는 경기도 지역이고, 사용자 기반은 아직 성장 단계입니다.

지금 당장 필요하지 않은 기능을 위해 팀 전체가 **RU 계산법, 파티션 키 설계, 일관성 수준(Consistency Level) 트레이드오프** 같은 Cosmos DB 고유의 개념을 학습하는 데 시간을 투자하는 것은 비용 대비 효과가 낮습니다.

PostgreSQL은 팀 전체가 이미 SQL과 관계형 DB에 익숙합니다. 이 친숙함은 단순한 편의가 아니라, **더 빠른 이터레이션, 더 낮은 버그 빈도, 더 명확한 데이터 모델**로 이어집니다. 그리고 PostGIS, pgvector라는 강력한 확장 기능은 PostgreSQL을 단순한 RDBMS 이상의 공간 데이터베이스이자 벡터 데이터베이스로 만들어 줍니다.

물론 이 결정에는 트레이드오프가 있습니다. 수십억 건의 데이터, 글로벌 멀티 리전 서비스로 성장한다면 그 시점에 Cosmos DB 또는 다른 분산 데이터베이스로의 마이그레이션을 재검토해야 할 것입니다. 그러나 그것은 성공적으로 서비스를 성장시킨 이후의 좋은 고민입니다. **지금은 빠르게 검증하고, 안정적으로 운영하며, 비용을 통제하는 것이 우선입니다.**

## 4. PostgreSQL을 더욱 강력하게 만드는 두 확장 기능

PostgreSQL을 선택한 결정을 최대한 활용하기 위해, 우리는 두 가지 핵심 확장 기능을 도입했습니다.

### 4.1 PostGIS — 공간 데이터의 표준

`PostGIS`는 PostgreSQL에 공간 데이터 타입, 인덱스, 함수를 추가하는 확장 기능입니다. 위치 기반 서비스에서 "내 위치 반경 3km 내 관광지 찾기"는 가장 기본적인 요구 사항인데, 이것을 위도/경도 좌표의 단순 수치 비교로 구현하면 지구의 곡률을 무시하게 되어 큰 오차가 발생합니다.

PostGIS의 `geography` 타입과 `ST_DWithin` 함수를 사용하면 WGS84 타원체 기반의 정확한 거리 계산이 가능합니다:

```sql
-- PostGIS: 정확한 구면 거리 계산
SELECT
    attraction_name,
    ST_Distance(
        ST_SetSRID(ST_MakePoint(127.0286, 37.2636), 4326)::geography,  -- 사용자 위치(수원)
        ST_SetSRID(ST_MakePoint(longitude::float, latitude::float), 4326)::geography
    ) AS distance_meters
FROM locallink.gyeonggi_attractions
WHERE ST_DWithin(
    ST_SetSRID(ST_MakePoint(127.0286, 37.2636), 4326)::geography,
    ST_SetSRID(ST_MakePoint(longitude::float, latitude::float), 4326)::geography,
    3000  -- 3,000미터 (3km) 반경
)
ORDER BY distance_meters ASC;
```

### 4.2 pgvector — PostgreSQL 안에 벡터 DB를 담다

`pgvector`는 PostgreSQL에 벡터 데이터 타입과 유사도 검색 인덱스를 추가하는 확장입니다. 1,536차원의 임베딩 벡터를 저장하고, 코사인 유사도(`<=>` 연산자)로 가장 관련성 높은 리뷰를 검색할 수 있습니다.

```sql
-- pgvector: 질문과 가장 유사한 리뷰 검색 (코사인 유사도)
SELECT
    attraction_name,
    clean_text,
    1 - (embedding <=> $1::vector) AS similarity  -- $1: 쿼리 임베딩 벡터
FROM locallink.attraction_reviews
ORDER BY embedding <=> $1::vector
LIMIT 5;
```

이 두 확장 기능 덕분에 PostgreSQL 하나로 **공간 데이터베이스 + 벡터 데이터베이스 + 관계형 데이터베이스**의 역할을 모두 수행할 수 있게 되었습니다. Pinecone, Weaviate 같은 별도의 벡터 DB 서비스를 도입하지 않아도 되므로, 인프라 복잡도와 비용이 동시에 줄어들었습니다. 이 선택의 구체적인 구현과 트레이드오프는 3부에서 깊이 다룹니다.

|-----------|------|------|-----------|
| 메인 DB | PostgreSQL Flexible Server | Azure Cosmos DB | 비용 예측 가능성, 관계형 모델 적합성, pgvector/PostGIS 통합 |
| 벡터 DB | pgvector (PostgreSQL 확장) | Pinecone, Weaviate, Azure AI Search | 관계형 메타데이터와의 조인, 인프라 단일화 |
| 수집 아키텍처 | Azure Functions (서버리스) | 상시 구동 서버 (App Service) | 간헐적 배치 워크로드에 맞는 이벤트 기반 트리거, 비용 최적화 |
| 스트리밍 버퍼 | Azure Event Hubs | 직접 DB 쓰기 | DB 보호(디커플링), 재처리 가능성, 파티션 키 기반 순서 보장 |
| 스트림 처리 | Azure Stream Analytics | Azure Databricks, Spark | 관리형 서비스, SQL-like SAQL, 간단한 윈도우 집계에 적합 |
| LLM (도슨트) | GPT-4o-mini | GPT-4, Claude, Gemini | 속도/비용 균형, 도슨트 스크립트 수준에 충분한 품질 |

| 시크릿 관리 | Azure Key Vault + Managed Identity | 환경 변수 하드코딩 | 보안 표준 준수, 코드에 크리덴셜 없음 |
